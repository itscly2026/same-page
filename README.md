# Same Page

Same Page 是一款面向合唱排练的乐谱 PWA。它让成员始终查看同一份 PDF 乐谱，并通过共享批注层与个人批注层记录排练要求、声部提示和个人记号。

应用以平板使用体验为优先，同时支持桌面和手机浏览器。安装为 PWA 后，已下载的乐谱和批注可以离线使用；重新联网后，修改会自动同步。

## 我们要解决的问题

合唱排练中常见的困难不是缺少 PDF 阅读器，而是每个人手中的谱面和标记逐渐变得不一致：

- 乐谱文件存在多个版本，页码和小节位置无法对应。
- 指挥或声部长的修改需要重复口头传达。
- 共享标记和个人标记混在一起，难以控制可见范围。
- 排练场地网络不稳定，在线应用无法成为可靠工具。

Same Page 的目标是让所有成员围绕同一份乐谱工作，同时保留每个人独立做笔记的空间。

## 核心体验

### 统一乐谱

- 管理员或获得授权的成员上传 PDF。
- 同一首作品只有一个当前版本，所有成员打开相同的谱面。
- 新版本发布后，应用会明确提示并更新本地离线副本。
- 乐谱可以被标记为“可离线使用”，并显示下载和更新状态。

### 分层批注

每一页乐谱上可以显示多个相互独立的批注层：

- **共享层**：用于指挥、声部长或其他获得授权的成员发布统一标记。系统预置全团、Soprano、Alto、Tenor 和 Bass 五个共享层。
- **个人层**：每位成员独有，只有本人可以读取和修改。

用户可以独立控制各层是否可见。进入绘制模式时，只编辑一个目标层，避免误改其他层。

### 批注工具

- 画笔：书写呼吸、力度、节奏和分句等记号。
- 橡皮：以整条笔迹为单位删除画笔内容。
- 文本：作为独立对象添加或删除简短的排练说明。
- 撤销与重做：作用于当前编辑会话和当前批注层。

所有批注都使用相对于 PDF 页面的归一化坐标，因此在不同屏幕尺寸和缩放比例下仍能保持对齐。

### 离线优先

- 应用外壳、已下载的 PDF、批注和用户偏好保存在浏览器本地。
- 编辑操作先写入本地数据库，成功后立即显示，不等待网络请求。
- 尚未上传的修改保存在 outbox 中，并显示明确的待同步数量和状态。
- 应用打开、恢复到前台或网络恢复时会尝试同步；用户也可以手动重试。
- 后台同步仅作为浏览器支持时的增强能力，不作为数据可靠性的前提。

## 用户与权限

Same Page 使用以下基本角色：

- **成员**：查看乐谱和共享层，编辑自己的个人层。
- **声部长／指挥**：拥有成员能力，并可编辑被授权的共享层。
- **管理员**：管理乐谱、成员和共享层权限。

权限由服务端根据已验证的用户身份决定。客户端提交的用户 ID、作者或角色字段不能作为授权依据。

个人层必须在所有服务端读取和写入路径中按当前用户隔离。删除乐谱、替换 PDF 和编辑共享层都需要显式权限。

## 技术架构

```text
React + TypeScript PWA
├── PDF.js：PDF 加载与页面渲染
├── SVG overlay：批注显示与编辑
├── IndexedDB：本地数据、同步游标和 outbox
└── Service Worker：应用外壳与离线资源缓存
                │
                │ HTTPS 同步
                ▼
Cloudflare Worker
├── 身份与权限校验
├── 乐谱、批注和同步 API
├── D1：结构化数据、版本和幂等记录
└── R2：带版本号的 PDF 文件
```

基础设施统一使用 **Cloudflare 国际版**：

- **Workers Static Assets** 托管 PWA 静态资源。
- **Cloudflare Worker** 提供同源 API，并负责认证、授权和输入校验。
- **D1** 保存乐谱元数据、成员权限、层配置、批注文档和同步记录。
- **R2** 保存 PDF 原文件及其历史版本对象。

批注不使用 Workers KV。批注同步需要明确的版本检查和事务语义，而 KV 的最终一致性不适合这类写入。

在当前非实时同步模式下不使用 Durable Objects。如果以后加入多人实时编辑或 WebSocket，再以单份乐谱作为协调单元引入。

## 数据模型

### Score

表示一份统一乐谱：

- `id`
- `title`
- `pdfVersion`
- `pdfObjectKey`
- `createdBy`
- `createdAt`
- `updatedAt`

PDF 使用不可变的版本对象，例如：

```text
scores/{scoreId}/{pdfVersion}.pdf
```

更新乐谱时创建新对象并切换 `pdfVersion`，不直接覆盖旧对象。客户端据此判断离线副本是否需要更新。

### Layer

表示一个可独立显示和授权的批注层：

- `id`
- `scoreId`
- `name`
- `color`
- `kind`: `shared` 或 `personal`
- `order`

个人层是产品概念，不允许客户端通过伪造 `layerId` 访问其他人的数据。个人层的所有者始终由服务端当前身份确定。

### AnnotationDocument

一个批注文档对应一页乐谱上的一个层：

- `scoreId`
- `page`
- `layerId`
- `ownerUserId`：个人层使用当前用户 ID，共享层为空
- `payload`
- `revision`
- `updatedAt`

`payload` 保存该页该层的笔迹和文本对象。每个对象都有稳定 ID，不通过内容比较重新推断身份。

以“页 + 层”为同步单位，可以让本地保存、权限检查和冲突处理保持简单，同时避免一次保存影响其他层。

## 同步模型

1. 用户编辑批注。
2. 应用在同一个 IndexedDB 事务中更新本地 `AnnotationDocument` 并写入 outbox。
3. 相同“页 + 层”的连续修改在 outbox 中合并，只保留需要上传的最新状态。
4. 客户端提交 `mutationId`、`baseRevision` 和新的 `payload`。
5. Worker 在 D1 事务中验证权限与版本，写入新 revision，并记录 `mutationId` 防止重试造成重复写入。
6. 成功后客户端移除对应 outbox 项，并保存新的 revision 和同步游标。

服务端不会根据“客户端快照中缺少某个对象”推断其他层或其他用户的数据应该被删除。

当 `baseRevision` 已过期时，服务端返回最新文档。客户端保留本地草稿，并提示用户选择服务器版本或本地版本；同步失败不能被显示为已保存到云端。

## PDF 加载与离线存储

- PDF.js 负责解析和渲染页面。
- 在线读取支持 HTTP Range，以避免首次打开时下载整份大文件。
- 用户选择离线下载后，完整 PDF 按版本缓存在本地。
- Service Worker 缓存应用外壳；IndexedDB 保存业务数据和离线状态。
- 应用请求浏览器持久化存储权限，并在无法保证持久存储时向用户说明。
- UI 分别展示“已保存到本机”和“已同步到云端”，不把两者混为一个状态。

## 设计原则

- **本地写入优先**：网络延迟和断网不能阻止用户做批注。
- **没有静默丢失**：错误、冲突和待同步状态必须可见。
- **权限在服务端执行**：前端隐藏按钮不是安全措施。
- **按领域对象建模**：批注层和 PDF 版本是业务概念，不泄漏绘图库内部 JSON。
- **先保持简单**：当前需求不需要实时协作、CRDT 或分布式协调服务。
- **平板优先**：触控、Apple Pencil／手写笔、缩放和误触防护优先于桌面快捷操作。

## 验收重点

- 同一批注在不同尺寸和缩放比例下保持准确对齐。
- 断网后可以打开已下载的乐谱并继续编辑。
- 关闭或刷新应用不会丢失未同步修改。
- 一个用户不能读取或覆盖另一个用户的个人层。
- 编辑个人层不会修改共享层，编辑一个共享层不会删除其他层的新内容。
- 同一个同步请求重复提交不会产生重复批注或重复版本。
- PDF 更新后，旧离线版本不会被误认为当前版本。
