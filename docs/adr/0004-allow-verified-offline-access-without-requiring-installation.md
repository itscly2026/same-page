# Allow verified offline access without requiring installation

The same Web/PWA product will work across devices without requiring installation. Offline availability is claimed only after the score and required annotation data have been fully stored and verified on that device. Every complete offline workspace is namespaced by an opaque local owner, choir, and score: authenticated owners derive from the Better Auth user ID, while guests receive an unshared device-local random owner. An expired online session does not block the last authenticated user from opening or editing that workspace, but synchronization requires the same user to reauthenticate. Activating another user invalidates the previous workspace before local results can be displayed or written. Explicit logout warns about unsynchronized work, removes private and mutable state, and moves only scrubbed synchronized shared content into a fresh guest workspace. PWA installation remains a strong recommendation rather than an access gate.

Opening a score automatically prepares the current display mode's offline copy without blocking online reading on successful storage or snapshot verification. A matching verified local copy has first choice, with a bounded wait so slow local storage cannot block the cloud path. PDF preparation reuses the displayed immutable version's bytes when available; the complete checksum, app shell and owner-scoped annotation checks still gate activation. Failures retain the previous copy and expose an explicit retry, rather than claiming that a viewed score is available offline.

Offline preparation is shared within one tab for the same local owner, effective session, drive, score, immutable PDF version and display mode. Reader automatic intent lasts only until that reader exits or changes target; the last automatic requester cancels an otherwise unowned task. An explicit download or retry owns the shared task across application navigation, including when it joins an automatic preparation. Closing the tab does not promise completion and no persistent background scheduler is introduced. Losing the confirmed online identity, logout or scoped file cleanup invalidates preparation regardless of intent; returning to the same user cannot reuse a prior session's task. Cross-tab coordination remains the activation transaction's owner/session, active-copy and cleanup fences.

Preparation state and verified-copy availability are independent. A pending or failed replacement never certifies the requested version or display mode, and a failure preserves any previously verified copy. Both reader and library observe structured preparation results through the offline module. The reader only selects its display target, first-display trigger and reusable PDF bytes; the library expresses explicit download intent.

Application entry restores the last local owner independently from online session confirmation. Checking, temporary network/service failure, and a confirmed absent session are distinct states; only a confirmed authenticated session enables cloud synchronization. Owner-scoped persisted drive directories are navigation metadata, not membership or downloaded-content evidence. Explicit logout removes those directories along with private local data. Reconfirming the same user updates the reader's online capability without replacing its local editing session or reading position.

Local file cleanup deletes only owner-authorized PDF/image records and advances a persistent owner/drive/score fence in the same transaction. Every download activation compares its captured fence, including downloads started before any active copy existed. Existing readers stop automatic preparation after cleanup, while held immutable blobs remain usable. New explicit opens may prepare another copy. Annotation state, outbox, conflicts, directory and login state are outside file cleanup.

The current drive directory and retained offline copies are independent. Complete successful directory responses replace directory membership; a confirmed deletion removes its entry immediately even when the subsequent refresh fails; local copies never fill absent entries. Retained copies remain discoverable under the current drive's local storage, with the same reader authorization and read-only recovery rules. Following confirmed access revocation, the same drive list instead shows only verified retained copies, preserving search and sort. The owner-scoped revocation marker persists across offline reopening and is replaced only by a successful directory response; missing authentication and transient failures do not create that marker. Metadata refresh can remove or update snapshot layers, but cannot certify newly discovered layer content as downloaded.

Application updates prepare in the background. The waiting worker asks every same-origin window/PWA before activation; missing replies veto activation. Each client also checks again before reloading. Reader routes, active exit/save guards, dialogs, focused input and in-progress operations prevent reload. Reliably saved drafts do not require cloud synchronization. About/update status identifies the running build separately from a prepared update.

Issue #221 separates immutable file records (`offlineScores`) from mutable, owner-scoped annotation snapshots (`offlineSnapshots`). Version 11 atomically extracts existing snapshots without resetting the database or changing draft, outbox, conflict or directory records. Layer refresh and drive-wide revocation transact only over annotation metadata and snapshots, never other scores' PDF/image Blobs. Activation, replacement, file cleanup and logout maintain both halves in one transaction. A missing snapshot cannot certify a file as an offline copy; restoration reads the current persisted snapshot and never falls back to a stale in-memory snapshot after cleanup.

Offline preparation performs a fresh layer request and complete content pull without pushing the local outbox. Unsynced intent remains in the annotation store and snapshot; an upload failure cannot block preparing otherwise complete readable content. A failed permission check or content pull still prevents activation, independently from successful PDF checksum validation. The UI distinguishes local file reads, offline preparation and annotation preparation/sync failures. Inspecting retained copies isolates an unreadable score instead of failing the whole drive list.
