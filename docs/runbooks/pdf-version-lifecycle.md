# PDF 候选、发布、回滚与清理

对应 Issue #97 工作包 B。迁移和代码须在同一发布窗口上线，不兼容旧客户端的立即替换请求；旧客户端会收到缺少修订号的错误，原文件不受影响。

## 上传验证

上传使用 `unpdf`/PDF.js 检查每页页面树、尺寸与绘图指令，再把原始 PDF 按不可变版本写入 R2。
限制以 [共享请求定义](../../src/shared/scores.ts) 和 [PDF 验证实现](../../worker/scores/pdf-validation.ts) 为准。
验证不逐页光栅化，也不保证各设备字体和渲染一致；单页解析仍受 Worker 内存与执行时间限制。
D1 用量字段与触发器原子限制云盘配额，客户端展示的用量不能替代服务端检查。
扫描 PDF 的实际像素与离线重开验证见 [解码资源 runbook](pdf-rendering-assets.md)。

## 状态与运营检查

- `pending` 是尚未完成对象写入的预留；超过一小时未完成可回收。
- 带 `candidate_expires_at` 的 `ready` 版本只供管理员预览；24 小时后不可发布/读取，下一次成功的小时清理回收。
- 发布/回滚使用预览时的 `version_revision`；原子更新指针、修订号和两侧保留期。回滚不会上传文件或复用编号。
- 历史版本过期立即不可回滚/读取；回收站仍保留全部历史 PDF 到乐谱回收期结束。
- 删除版本通过已有触发器释放逻辑配额并加入 `score_object_deletions`；R2 删除失败保留队列，后续运行重试。未删除文件不会被重新引用。
- 清理每次最多处理 100 份到期乐谱、100 个版本和 100 个队列对象；积压可能让物理删除晚于到期时刻。检查小时任务错误和队列积压，不把逻辑配额当作实际 R2 占用。

## 发布与恢复验证

1. 运行 `npm run check:full`，核对 migration `0013_safe_pdf_replacement.sql`。迁移只增加字段、索引、触发器并回填历史最大编号，不删除现有 PDF/批注。
2. 生产迁移前记录版本数、当前指针、云盘配额和删除队列数量，确认可使用 D1 的既定备份恢复机制；不要导出身份、凭据或批注内容到日志。
3. 随 Worker 发布迁移；更新 PWA。用管理员上传候选，确认另一成员仍读取旧版、取消后旧版不变。
4. 发布一次，回滚原版，再次打开验证实际 PDF、页数、批注和离线副本更新提示。两个管理员窗口同时操作，只有基于最新修订的操作成功。
5. 在隔离测试云盘验证到期候选/历史清理、R2 删除失败重试；不得为了验收修改真实用户版本的到期时间。
6. 若要恢复应用代码，保留数据库新增字段并暂停受影响写入，避免回退到绕过确认的旧替换端点。数据恢复需要核对 D1 指针对应的 R2 文件仍存在；已物理删除的 PDF 不能仅靠 D1 恢复。

生产迁移、定时清理上线与实际 iPad/Android 逐页预览、离线替换验证仍需各自的发布/设备证据；本地测试不能替代。
